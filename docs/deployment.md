# Render Deployment Guide

Status: the academic deployment checks were completed on 2026-09-14 and are recorded in [Phase 6](verification-results/phase-6.md). This guide remains the required procedure for any redeployment or for verifying a newer exact commit. Phase 6 identifies the precise deployed revision and does not claim deployment of a later revision without a recorded Render deployment identifier.

## Fast path: commit to a live demo

Use this sequence when the code is already reviewed and the goal is to get a presentation URL:

1. Run the local checks in [Pre-deployment checks](#pre-deployment-checks).
2. Push the reviewed branch to GitHub.
3. Create or update a Render Blueprint from `render.yaml`.
4. Set the server-only variables in [Required server variables](#required-server-variables).
5. Deploy, wait for `/api/health` to return HTTP 200, and copy the Web Service URL.
6. Enter the shared access code and run [Staging acceptance](#staging-acceptance).
7. Record the URL, commit SHA, date, and pass/fail evidence without recording secrets.

The repository branch and Render service are separate concerns: pushing to GitHub makes the commit available to Render, but it does not create Render resources or supply secrets automatically.

## Pre-deployment checks

Run these commands from `nutrition-coach/` before creating a Blueprint or redeploying:

```bash
npm ci
npm run format:check
npm run lint
npm run typecheck
npm run test:unit
npm run security:check
npm run build
```

The Playwright suite needs Chromium. Its global setup uses dedicated test-only access and signing values and authenticates through the real access endpoint:

```bash
npm run test:e2e
```

The deployed service must keep `DEMO_ACCESS_CODE` enabled. Never commit `.env.local`, API keys, database URLs, signed cookies, or real user data.

For the academic submission, create the ZIP without `.git` or local environment files, then inspect the completed archive:

```bash
npm run security:archive -- /path/to/submission.zip
```

The archive check permits `.env.example` but rejects every other `.env*` file, all `.git` metadata, recognized nested archive containers, and common credential patterns within its byte limits. It is a safeguard against accidental submission contents, not a general detector for encryption or every possible encoding.

## Architecture

`render.yaml` creates:

- one free Node Web Service running the Next.js application; and
- one free Render PostgreSQL database.

The Web Service starts `next start` immediately so Render can detect the listening port. The `/api/health` endpoint requires `DATABASE_URL` in production, initializes the SQL schema, validates the database connection, and seeds both profile fixtures and the baseline catalog before reporting healthy. It returns a generic `503` instead of falling back to memory when production persistence is missing or unavailable. [Render documents](https://render.com/docs/free) that free PostgreSQL expires after 30 days, provides 1 GB, and has no backups; use it only for the short course presentation. The resource definitions follow Render's [Blueprint specification](https://render.com/docs/blueprint-spec).

## Required server variables

- `DATABASE_URL` — supplied by `fromDatabase.connectionString`, which resolves to the same-region Render internal private-network URL.
- `DATABASE_SSL` — intentionally unset for this academic Render Blueprint's internal connection. Set it to `require` for an external URL only when its certificate can be verified.
- `DATABASE_CA_CERT` — optional trusted PEM CA certificate for a TLS connection whose certificate does not chain to a public CA. Escaped `\\n` line breaks are accepted.
- `DEMO_ACCESS_CODE` — choose one shared code for the lecturer demo.
- `COOKIE_SIGNING_SECRET` — generated by Render; at least 32 random characters if set manually.
- `OPENAI_API_KEY` — server-side OpenAI project key.
- `OPENAI_MODEL` — defaults to the model declared in `render.yaml`.
- `OPENAI_CONTEXT_WINDOW` — optional context-window size used to trigger conversation compaction; defaults to `128000`.
- `USDA_FDC_API_KEY` — server-side data.gov key for USDA FoodData Central.

Never put real values in `.env.example`, Git, browser code, screenshots, or verification logs.

`DATABASE_URL` must not contain `ssl`, `sslmode`, `sslcert`, `sslkey`, or `sslrootcert` query parameters. The application and migration command reject those parameters so URL parsing cannot replace explicit TLS settings. Render's internal URL stays on the same-region private network and this academic deployment accepts it without TLS. For any external database URL, set `DATABASE_SSL=require`, supply a trusted CA when needed, and keep certificate verification enabled.

The production response policy includes a same-origin Content Security Policy. It permits inline scripts and styles for Next.js compatibility, so it limits external sources but is not a complete XSS defense. CSP and HSTS are production-only; the remaining browser headers also apply during local development.

Production access also fails closed: if `DEMO_ACCESS_CODE` is absent or `COOKIE_SIGNING_SECRET` is absent or shorter than 32 characters, `/api/demo/access` returns a generic `503`, sets no cookie, and protected routes remain inaccessible. Do not use a temporary hard-coded fallback in a deployment.

## Create the services

1. Push the reviewed branch to GitHub:

   ```bash
   git status --short
   git log -1 --oneline
   git push origin <reviewed-branch>
   ```

2. In Render, create a new Blueprint and select this repository.
3. Review the two resources from `render.yaml`.
4. Confirm the Web Service uses `npm ci && npm run build` for build and `npm run start:render` for start, with `/api/health` as its health check. The server must start before the health check initializes the database.
5. Enter the three manually synchronized secrets: `DEMO_ACCESS_CODE`, `OPENAI_API_KEY`, and `USDA_FDC_API_KEY`.
6. Deploy and wait for `/api/health` to return HTTP 200.
7. Open the Web Service URL and enter the shared access code.

If Render asks for a region, keep the Web Service and database in the same region. Use the free plans only for the short course presentation.

The free Web Service may spin down when idle. The first request after inactivity can therefore be slower than normal.

## Verify the first deployment

After the service reports healthy:

```bash
curl --fail --silent --show-error https://<service-host>/api/health
```

Then open `https://<service-host>` in a private browser window. The entry view must show exactly **New Demo Profile** and **Existing Demo Profile** after the shared code is accepted. If the health check fails, inspect the Render logs for migration, database, or missing-environment-variable errors before testing the UI.

## Staging acceptance

Run this checklist against the deployed URL:

1. Open Fresh and Existing in separate tabs and confirm both cloud states load.
2. Change Fresh, then reload it. Confirm the state persists and Existing is unchanged.
3. Reset Fresh. Confirm only Fresh returns to empty onboarding.
4. Add or edit an Existing weight, reload, then reset Existing. Confirm the original plan and seeded history return.
5. Ask for jasmine rice in the main coach chat. Confirm the named food starts a search before any variant question, choose one of at most five USDA candidates, inspect the approval card, and reject it once.
6. Correct the query, approve the record, and confirm it is selected for the requesting profile.
7. Open the other profile and confirm the food is available centrally but is not selected there.
8. If planning is complete, approve another runtime food and confirm the application creates only a new Draft containing it; the Active Plan remains unchanged.
9. Search for tomato and pasta and confirm only Foundation Foods or SR Legacy candidates appear.
10. Exercise one controlled source failure. Confirm that the AI estimate appears only after clicking **Use an AI estimate** and remains labelled `AI estimate · USDA not verified`.
11. Reset both demos separately and confirm the runtime food remains in the central catalog.
12. Verify a wrong access code is rejected and no protected route or state endpoint is usable without the signed cookie.
    Do this once with an authorized test code; do not perform repeated guessing against the shared anonymous attempt bucket.
13. Send one English and one Hebrew coach turn and confirm streamed, language-matched replies plus persisted conversation after reload.
14. Select a USDA candidate using text such as “the fifth one,” then verify typed “approve it” does not approve it and the visible Approve button does.
15. Open the same profile in two tabs, start concurrent turns, and confirm the second receives a recoverable conflict without duplicate transcript entries.

Record the deployed URL, commit SHA, date, conversation and lookup examples, screenshots, and pass/fail results in `docs/verification-results/turn-8.md`. Do not record secret values.

## Live security verification

After each production deployment, verify the deployed commit rather than assuming a successful build applied the configuration.

1. Request `/api/health` and confirm `200` without exposing configuration or database details.
2. Inspect both the page and `/api/health` response headers. In production they must include `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, and `Permissions-Policy`.
3. Confirm the public endpoint has a valid TLS certificate. This confirms the browser-to-Render edge connection only; it does not verify the Web Service-to-PostgreSQL connection.
4. Confirm that the Blueprint supplied the same-region internal database hostname and that both migration and application connections succeed. Do not copy the URL, hostname, credentials, or secret values into documentation. If an external database URL is used instead, confirm `DATABASE_SSL=require` and certificate verification.
5. Run `npm run security:archive -- <final-submission.zip>` on the exact archive being submitted. The command rejects Git history, local environment files, nested archives, and common credential patterns.

If the expected headers are absent, treat the deployment as an older or misconfigured build and do not record the live security gate as passed.

Raw application, database, OpenAI, or USDA exception messages must not appear in page, JSON, or streamed responses. Use server logs for redacted diagnostics and expose only the documented generic message and stable safe code to the browser.

## Updating an existing deployment

1. Run the pre-deployment checks again.
2. Push the reviewed commit to the branch connected to the Blueprint.
3. Watch the Render build, migration, and health-check logs.
4. Run the health check and the smallest applicable staging scenario before the presentation.
5. Fix failures in source control and redeploy; do not hot-edit application code in the running service.

The migration command is idempotent. Use the profile-specific **Reset demo** controls for demo data recovery; do not manually delete database tables or profile rows.

## Troubleshooting

### The access gate repeats

Confirm that `DEMO_ACCESS_CODE` is set on the Web Service, the entered value matches exactly, and the browser accepts the signed cookie. Do not disable the gate in Render.

### Coach turns fail

Check `OPENAI_API_KEY`, `OPENAI_MODEL`, and the safe failure code in the Render logs. The application should preserve confirmed state and show Retry. Do not copy model output or secrets into evidence files.

### Food lookup fails

Check `USDA_FDC_API_KEY`, source limits, and the safe lookup stage. A timeout, `403`, `429`, malformed response, or no genuine match must leave the catalog and Active Plan unchanged. The optional AI estimate is allowed only after explicit opt-in and remains labelled unverified.

### The first load is slow

The free Web Service may be sleeping. Wait for the visible loading state instead of submitting the same action repeatedly; command IDs and server-side turn locking make retries idempotent.

## Operational limits

- Before access is granted, all users share one anonymous limit of five access-code attempts per 15 minutes. This avoids trusting spoofable forwarding headers, but one user can temporarily exhaust the shared bucket and block other users until the window expires.
- 10 lookup workflows per hour for the same verified, hashed access session.
- 30 lookup workflows per day globally.
- 30 AI conversation turns per hour for the same verified, hashed access session.
- 100 AI conversation turns per day globally.
- One pending agent turn per shared profile; a turn older than 90 seconds becomes recoverable.
- USDA source requests abort after 15 seconds.
- Search is restricted to Foundation Foods and SR Legacy and returns at most five candidates.
- The browser selects an application candidate UUID, never an arbitrary USDA identifier or URL.
- USDA response bodies and API credentials are never sent to the model or browser.
- Assistant responses stream from the Web Service, but server processing and persistence continue if the browser disconnects.

## Database expiry

Schedule the free database close to the presentation date. Render currently expires free PostgreSQL after 30 days and deletes it after the documented grace period unless upgraded. Reset does not replace the database expiry policy and there are no free-tier backups.
