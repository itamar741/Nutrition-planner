# Render Deployment Guide

Status: configuration is committed and locally verified. The final staging checklist requires the project owner's Render, OpenAI, and ScrapingBee credentials.

## Architecture

`render.yaml` creates:

- one free Node Web Service running the Next.js application; and
- one free Render PostgreSQL database.

The Web Service runs the SQL migration before `next start`. The health endpoint then validates and seeds both profile fixtures and the baseline catalog. [Render documents](https://render.com/docs/free) that free PostgreSQL expires after 30 days, provides 1 GB, and has no backups; use it only for the short course presentation. The resource definitions follow Render's [Blueprint specification](https://render.com/docs/blueprint-spec).

## Required server variables

- `DATABASE_URL` — supplied from the Render database by the Blueprint.
- `DATABASE_SSL=require` — set by the Blueprint.
- `DEMO_ACCESS_CODE` — choose one shared code for the lecturer demo.
- `COOKIE_SIGNING_SECRET` — generated by Render; at least 32 random characters if set manually.
- `OPENAI_API_KEY` — server-side OpenAI project key.
- `OPENAI_MODEL` — defaults to the model declared in `render.yaml`.
- `SCRAPINGBEE_API_KEY` — server-side ScrapingBee key.

Never put real values in `.env.example`, Git, browser code, screenshots, or verification logs.

## Create the services

1. Push the reviewed branch to GitHub.
2. In Render, create a new Blueprint and select this repository.
3. Review the two resources from `render.yaml`.
4. Enter the three manually synchronized secrets: `DEMO_ACCESS_CODE`, `OPENAI_API_KEY`, and `SCRAPINGBEE_API_KEY`.
5. Deploy and wait for `/api/health` to return HTTP 200.
6. Open the Web Service URL and enter the shared access code.

The free Web Service may spin down when idle. The first request after inactivity can therefore be slower than normal.

## Staging acceptance

Run this checklist against the deployed URL:

1. Open Fresh and Existing in separate tabs and confirm both cloud states load.
2. Change Fresh, then reload it. Confirm the state persists and Existing is unchanged.
3. Reset Fresh. Confirm only Fresh returns to empty onboarding.
4. Add or edit an Existing weight, reload, then reset Existing. Confirm the original plan and seeded history return.
5. Search for one cooked food. Confirm no cooked/raw clarification is requested solely because cooking was omitted, choose one of at most five Fuder candidates, inspect the approval card, and reject it once.
6. Correct the query, approve the record, and confirm it is selected for the requesting profile.
7. Open the other profile and confirm the food is available centrally but is not selected there.
8. If planning is complete, approve another runtime food and confirm the application creates only a new Draft containing it; the Active Plan remains unchanged.
9. Search for one packaged product and verify brand or serving clarification where materially needed.
10. Exercise one controlled source failure. Confirm that the AI estimate appears only after clicking **Use an AI estimate** and remains labelled `AI estimate · Fuder not verified`.
11. Reset both demos separately and confirm the runtime food remains in the central catalog.
12. Verify a wrong access code is rejected and no protected route or state endpoint is usable without the signed cookie.

Record the deployed URL, commit SHA, date, lookup examples, screenshots, and pass/fail results in `docs/verification-results/turn-4.md`. Do not record secret values.

## Operational limits

- 10 lookup workflows per hour for the same hashed session or IP.
- 30 lookup workflows per day globally.
- Fuder source requests abort after 35 seconds.
- ScrapingBee scenarios remain below its documented [40-second scenario limit](https://www.scrapingbee.com/documentation/js-scenario/).
- Search returns at most five allowlisted `/foods/` links.
- No premium, stealth, bypass, login, bulk crawling, or arbitrary URL mode is enabled.
- Raw source HTML is never sent to the model or browser.

## Database expiry

Schedule the free database close to the presentation date. Render currently expires free PostgreSQL after 30 days and deletes it after the documented grace period unless upgraded. Reset does not replace the database expiry policy and there are no free-tier backups.
